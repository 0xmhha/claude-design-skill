## 3 specific asks 의 핵심 phrasing

### Ask 1 — Trial 동의

> "다음 1주 RescueTime (또는 Toggl) 를 깔고 본인이 figma 또는 ai 도구 사용한 시간을 자동 측정해주실 수 있나요? 결과는 본인이 raw data 다 갖고, 본인 동의 후에만 *aggregate 형태* (몇 시간 × 어느 도구) 만 저한테 공유. 진짜 *그 20시간 낭비* 가 self-report 인지 measurable 인지가 본 prototype 가치 판단의 single point 라서요."

→ 핵심: *control 은 Anchor-A 측*, founder 는 aggregate 만. D5 grilling 의 bias 통제 3중 의 첫 piece.

### Ask 2 — Paper mockup Venmo response

> "(컴포넌트 3 1 page 보여주며) 이게 작동한다면 — AI 가 만든 design 이 figma 에 자동으로 layer 이름까지 들어가는 거 — Venmo 보내고 싶으신가요?" (직설)

→ 응답 카테고리:
- **"Venmo 보내고 싶다"** (또는 비슷한 강한 긍정) → A approach build 시작
- **"not exactly"** / "괜찮은데..." (hedge) → wedge 재구성 필요. *어떤 부분이 missing 인지* follow-up
- **"이미 figma 공식이 그거 안 해?"** (PRE-02 의 wedge thin 화 위험) → 3 piece (session/collision/naming) 의 differentiation 설명 + 다시 Venmo 질문

### Ask 3 — Walkthrough recording

> "지난 1-2주 작업 중에 layer naming 이나 'figma 에서 같은 작업 또 하네' 라고 짜증 났던 순간 있어요? 그 figma file 직접 열고 *어디서 왜 짜증 났는지* 보여주실 수 있을까요? 녹취해도 될까요? 본인 회사 정보 보이는 부분은 가리면서 진행."

→ 핵심: 녹취 동의 + PII (회사 정보) 보호. D2 grilling 의 verbalization skill measure baseline.

# Component 2: Behavioral Observation Tooling Setup Guide

## 측정 architecture

```
[Anchor-A device]
    ├── 작업관리 툴 (Linear / Jira / Notion / 사내 선호)
    │   └── 작업 시작 시간 / 완료 시간 (이미 기록 중 — D5 grilling 사용자 답)
    │
    └── RescueTime (또는 Toggl)
        └── App 사용 시간 (figma / chatgpt / claude-code / etc.)

[Anchor-A 측 합산]
    └── 작업별 raw report (json/csv)
            │
            ▼
[Aggregator script (Anchor-A 가 실행)]
    └── aggregate-only output
        - 작업 카테고리 × 도구 × 시간 (총합)
        - 본인 과거 baseline 비교 (같은 작업 카테고리)
        - 개인 식별 없는 형식
            │
            ▼
[founder]
    └── aggregate 결과만 수신
```

## Tool 선택 권장

### 작업관리 툴
- 사내 현재 사용 중인 것 그대로 (Linear / Jira / Notion / 사내 sheet 등)
- 단 *시작 시간 + 완료 시간 + 작업 카테고리* (라벨/태그) 3 필드 필수
- 컨펌 완료 (D5-Q1.b 의 "완성 컨펌") 가 *완료 시간* 기준

### App 사용 시간
- **RescueTime** (권장) — Mac/Windows. 자동 백그라운드 측정. 결과는 본인 dashboard.
- 대안: **Toggl Track** — manual timer 기반. 이미 사용 중이면 그대로.
- 대안: **ActivityWatch** — open source, self-host. privacy 우선 사용자.

### Aggregator script
- Anchor-A 가 실행할 단순 Python/JS script — RescueTime export csv + 작업관리 툴 export 받아서 *작업 카테고리 × 도구 × 시간* 집계
- founder 가 1-2시간 작성 + Anchor-A 에게 전달 (또는 spreadsheet 템플릿 으로 대체 가능)
- *raw 개인 데이터 는 Anchor-A 측에만 보관*, aggregate 만 founder 공유

## 측정 metric (1주 trial)

| Metric | Formula | Purpose |
|--------|---------|---------|
| **시간 절감 율** | (과거 baseline 시간 - trial 주 시간) / 과거 baseline 시간 | P2 의 wound 검증 — *진짜 20h/week* 인지 |
| **AI 도구 사용 빈도** | trial 주 의 figma + claude-code + chatgpt 시간 비율 | self-report 한 시간 vs 실측 차이 |
| **컨펌 round 수** | 작업 1 개당 컨펌 시도 → 수정 → 재컨펌 cycle 수 | D2 grilling 의 judging skill 변화 baseline |
| **prompt 빈도 / 시간** | trial 주 의 claude-code 호출 수 | D2 grilling 의 verbalization skill 변화 baseline |

## Aggregate-only data pipeline 설계

```yaml
# Aggregator script 출력 예시 (founder 공유 형식)
trial_week: 2026-06-01 to 2026-06-07
participant_id: anchor-a  # 익명 placeholder
task_count: 5
total_hours: 18.3
breakdown_by_tool:
  figma: 9.2 hours
  claude_code: 1.1 hours
  chatgpt: 0.8 hours
  other: 7.2 hours
breakdown_by_task_category:  # 작업관리 툴의 라벨 기반
  landing_page: 4.5 hours
  component_design: 6.8 hours
  documentation: 1.0 hours
  other: 6.0 hours
confirmation_round:
  total_tasks: 5
  avg_rounds_per_task: 2.4
  max_rounds: 4
historical_baseline:  # 같은 카테고리의 본인 과거 평균
  landing_page_avg: 5.8 hours  # trial 주 = 4.5 → -22%
  component_design_avg: 7.1 hours  # trial 주 = 6.8 → -4%
```

## 본인 과거 baseline 비교 방법

1. Anchor-A 측에서 *최근 3 개월* 의 *동일 카테고리* 작업 데이터 export
2. 작업 카테고리 별 평균 시간 계산 (baseline)
3. Trial 주의 시간 - baseline = delta
4. **20% 이상 단축** = wound 검증 ✓ / **5% 이하** = itch 의심 / **0% 또는 +** = wound 가설 깨짐 (re-scope)

→ threshold 는 trial 결과 보고 founder 가 평가. 미리 hardcode 안 함 (small N 의 small sample 에서 hardcode 는 false confidence).

# Component 4: U-01/U-02 검증 Cheat Sheet

## Setup (미팅 전 founder 측 준비)

```bash
# claude-code + figma plugin install
claude plugin install figma@claude-plugins-official

# 또는 manual
claude mcp add --transport http figma https://mcp.figma.com/mcp

# install 확인
claude mcp list  # figma server 가 listed 인지
```

미팅 시 본인 노트북에 위 설정 완료된 상태로 입장.

## U-01: Atomic Batch Write 검증

### 절차

1. Anchor-A 의 figma file 열기 (Anchor-A 측 paid account)
2. 5 layer 선택 (예: 5 rectangle)
3. claude-code 에서 prompt:

```
다음 5 layer 의 이름을 한 호출에 변경:
- Rectangle 1 → home__hero__bg
- Rectangle 2 → home__hero__cta  
- Rectangle 3 → INVALID_LAYER_ID_TO_TRIGGER_FAILURE
- Rectangle 4 → home__features__card1
- Rectangle 5 → home__features__card2

(3번째 의도적 invalid — partial failure 시 다른 4개가 commit 됐는지 확인)
```

4. 결과 inspect:
   - **All 5 reverted (atomic ✓)**: U-01 = atomic guarantee 존재. autoplan D-01 의 verify+diff 는 단순 logging 으로 충분.
   - **4 committed + 1 failed (non-atomic)**: U-01 = atomic 부재. D-01 의 rollback script 필수 구현.

### 응답 record 위치

본 미팅 결과 → `docs/2026-05-21-figma-mcp-inventory.md` 의 U-01 row 업데이트.

## U-02: Timestamp Field Inspect

### 절차

1. 같은 figma file 의 임의 frame 의 node-id 추출 (URL 의 `?node-id=X-Y` 형식)
2. claude-code 에서 prompt:

```
get_metadata 또는 get_design_context 호출해서 다음 node-id 의 응답 JSON 을 그대로 보여줘:
node-id: [X-Y from step 1]
```

3. 응답 JSON inspect — 다음 필드 search:

| 필드명 후보 | 의미 |
|------------|------|
| `lastModified` / `modifiedAt` / `updatedAt` | modification timestamp 존재 |
| `version` | version-based concurrency 가능 |
| `lastModifiedBy` | 누가 변경 — multi-user 추적 |
| (none of above) | timestamp 미지원 — file-level fallback |

4. 결과:
   - **layer-level timestamp 지원**: D3 의 scan-on-restart 가 fine-grained 작동. 효율 좋음.
   - **file-level 만 지원**: scan-on-restart 가 *어떤 layer 가 바뀌었는지 모름* → 전체 scan 강제. UX cost minor (1000+ element 시 latency).
   - **timestamp 미지원**: scan-on-restart 가 *항상 전체 scan*. 단 D3 의 page-level collision detection 는 layer name 비교만으로 fallback 가능 — 결정적 문제 없음.

### 응답 record 위치

`docs/2026-05-21-figma-mcp-inventory.md` 의 U-02 row 업데이트.

## U-03 (선택, 시간 남으면): Conditional Write 검증

### 절차

1. `use_figma` 의 input schema inspect:

```bash
# Claude 에게:
claude-code 의 figma plugin 의 use_figma tool input schema 를 보여줘. 특히 'if-match' / 'expected-version' / 'etag' 같은 conditional write 필드 있는지.
```

2. 결과:
   - **conditional write 필드 존재**: optimistic concurrency 지원. D3-Q2 β 구현 가능.
   - **부재**: D3-Q2 α (CLI lock) 가 그대로 default. mitigation 충분.

### 응답 record 위치

`docs/2026-05-21-figma-mcp-inventory.md` 의 U-03 row 업데이트.

## Decision Tree — 다음 세션 진입 시 자동 분기

```
C1 (trial 동의) == no
├── 다음 세션: wedge 재구성 + sample 재정의
└── /buddy:validate-idea 또는 office-hours 재진입

C1 == yes 이면 ↓

C3 (paid plan) == Starter/View/Collab
├── 다음 세션: ICP 재정의 (Anchor-A 가 paid 가능 환경 확인 / 다른 anchor 찾기)
└── (또는) trial 을 read-only ops 한정 진행

C3 valid + C2 (Venmo response) 분류:
│
├── 강한 긍정 ("Venmo 보낼래" / "지금 사고 싶다")
│   └── C4 (trial 데이터) 검토:
│       ├── 시간 절감 ≥ 20%
│       │   └── /buddy:plan-build 진입 — A approach 3-5일 task graph
│       │       (I1-I6 의 결과로 plan-build 의 effort/risk 정교화)
│       ├── 5-20%
│       │   └── wedge sharpening + I4 walkthrough memo 로 3 piece 우선순위 결정
│       │       → 우선순위 piece 단독 ship 후 데이터 재수집
│       └── ≤ 5% 또는 +
│           └── wound 가설 깨짐 → /buddy:validate-idea 재진입 (Stage 1 from scratch)
│
├── 조건부 긍정 ("X piece 가 진짜 가치")
│   └── 어느 piece (1=session / 2=collision / 3=naming) 가 가치 — follow-up 결정
│       → 그 piece 우선 ship + 다른 piece 후속
│
├── Hedge ("괜찮은데...")
│   └── follow-up 질문: "어떤 점이 missing?"
│       → wedge 재구성 또는 추가 grilling (D1 / D4)
│
└── 무관심 ("이미 figma 공식이 그거 안 해?") — N5 quote 확인
    └── PRE-02 의 wedge thin 화 risk *실현*:
        ├── differentiation 재pitch 가 즉석에서 통하면 → 강한 긍정 path 재진입
        └── 안 통하면 → wedge 폐기 또는 *figma-power 위의 free skill* 으로 reposition
```

## 다음 세션 진입 시 founder 가 들고 와야 할 minimal 패키지

```yaml
# Anchor-A trial 결과 (다음 세션 입력)

session_meta:
  meeting_date: YYYY-MM-DD
  trial_period: YYYY-MM-DD to YYYY-MM-DD
  pii_redacted: true  # 모든 quote/screenshot 의 PII 제거 완료

critical:
  C1_trial_consent: yes | no
  C2_venmo_response:
    raw_quote: "Anchor-A 의 정확 단어 (한국어 원본)"
    category: strong_positive | conditional | hedge | indifferent
  C3_figma_plan: "Professional / Org / Enterprise + seat type"
  C4_trial_data:  # Component 2 의 yaml 형식 그대로
    trial_week: ...
    total_hours: ...
    breakdown_by_tool: {...}
    breakdown_by_task_category: {...}
    confirmation_round: {...}
    historical_baseline: {...}

important:
  I1_atomic: all_reverted | partial_commit | other
  I2_timestamp: layer-level | file-level | none
  I3_conditional_write: yes | no
  I4_walkthrough_memo: "10-20 lines text + screenshot path"
  I5_confirmation_round_baseline: {past_avg: N, trial_avg: M}
  I6_prompt_frequency: {per_task: N, per_week: M}

nice_to_have:
  N1_additional_trial_users: 0..n
  N2_internal_group_consent: yes | no | partial
  N3_other_ai_tools: {tool_name: hours, ...}
  N4_naming_preference_examples: ["예시1", "예시2", ...]
  N5_indifferent_quote: "Anchor-A 의 무관심 raw 또는 null"
```

이 yaml block 을 다음 세션 첫 메시지에 paste 하면 → 자동 decision tree 분기 → wedge 결정 / plan-build / re-scope 즉시 진행 가능.
